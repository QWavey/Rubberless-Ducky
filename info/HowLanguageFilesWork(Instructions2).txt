## How Keyboard Layout (Language) Files Work

The language JSON files map **characters/keys** to **USB HID keycodes**. Let me break down the format and how the compiler uses them.

### The Keycode Format: `"modifier,reserved,keycode"`

Each entry is a three-part string: `"modifier, reserved, keycode"`

| Position | Name | Purpose | Example Values |
|----------|------|---------|----------------|
| First | **Modifier** | Shift, Ctrl, Alt, GUI flags | `00` (none), `01` (Ctrl), `02` (Shift), `04` (Alt), `08` (GUI) |
| Second | **Reserved** | Always `00` for standard HID | `00` |
| Third | **Keycode** | The actual USB HID usage ID | `04` (a/A), `28` (Enter), `1e` (1/!) |

### How the Compiler Parses This

Looking at the `getBytesForKey()` function from your code:

```javascript
function getBytesForKey(k, fullwidth=false) {
    let c = IDE_CONFIG['ducky_lang'][k];  // Get the string like "00,00,04"
    let codes = c.split(',');              // Split into ['00', '00', '04']
    
    if (codes[2] !== '00') {
        // Has a keycode
        keyCodes = [codes[2], codes[0]];   // Returns [keycode, modifier]
        // Example: 'a' -> ['04', '00']
        // Example: 'A' -> ['04', '02']  (same keycode, shift modifier)
    } else {
        // Just a modifier key
        keyCodes = [codes[0]];              // Returns just the modifier
        // Example: 'CTRL' -> ['01']
    }
    return keyCodes;
}
```

### Examples from Your German Layout

| Character | Entry | Parsed | Injected Bytes | Why |
|-----------|-------|--------|----------------|-----|
| `"a"` | `"00,00,04"` | `['04', '00']` | `04 00` | No modifier, keycode 04 |
| `"A"` | `"02,00,04"` | `['04', '02']` | `04 02` | Keycode 04 + Shift modifier |
| `"1"` | `"00,00,1e"` | `['1e', '00']` | `1e 00` | No modifier, keycode 1e |
| `"!"` | `"02,00,1e"` | `['1e', '02']` | `1e 02` | Same keycode 1e + Shift |
| `"ä"` | `"00,00,34"` | `['34', '00']` | `34 00` | German umlaut as keycode 34 |
| `"Ä"` | `"02,00,34"` | `['34', '02']` | `34 02` | Same keycode 34 + Shift |
| `"CTRL"` | `"01,00,00"` | `['01']` | `01` | Just modifier, no keycode |
| `"ALT"` | `"04,00,00"` | `['04']` | `04` | Just modifier |
| `"CTRL-ALT"` | `"05,00,00"` | `['05']` | `05` | Combined modifier (01 \| 04 = 05) |
| `"ENTER"` | `"00,00,28"` | `['28', '00']` | `28 00` | No modifier, keycode 28 |

### How Modifier Combinations Work

The compiler can OR (combine) modifiers together. For `CTRL-ALT` already combined as `05`, or `CTRL ALT t`:

```javascript
// For "CTRL ALT t" in DuckyScript:
// 1. Lookup 'CTRL' -> modifier '01'
// 2. Lookup 'ALT' -> modifier '04'  
// 3. OR them: 01 | 04 = 05
// 4. Lookup 't' -> keycode '17', modifier '00'
// 5. Inject: keycode ('17'), combined modifier ('05')
// Final: ['17', '05']
```

### Why Different Layouts Matter

The same character can have **different keycodes** on different keyboard layouts:

| Character | US Layout | German Layout | Physical Key |
|-----------|-----------|---------------|--------------|
| `"z"` | `1d` (keycode 1d) | `1c` (keycode 1c) | US: Z key, German: Y key |
| `"y"` | `1c` (keycode 1c) | `1d` (keycode 1d) | US: Y key, German: Z key |
| `"-"` | `2d` (keycode 2d) | `38` (keycode 38) | Different physical keys |

### The Injection Process

When you write `STRING Hallo` with a German layout:

1. `'H'` → lookup → `"02,00,0b"` → inject `['0b', '02']` (keycode 0b + shift)
2. `'a'` → lookup → `"00,00,04"` → inject `['04', '00']`
3. `'l'` → lookup → `"00,00,0f"` → inject `['0f', '00']`
4. `'l'` → lookup → `"00,00,0f"` → inject `['0f', '00']`
5. `'o'` → lookup → `"00,00,12"` → inject `['12', '00']`

Final `inject.bin` bytes: `0b 02 04 00 0f 00 0f 00 12 00`

### Summary

The language JSON tells the compiler: **"For this character/key, use this keycode and these modifier flags"** - allowing the same DuckyScript payload to work correctly on different physical keyboard layouts by outputting the correct keycodes for that layout.


IMPORTANT:
LANGUAGE KEYCODES GET COMPILED INTO THE FIRMWARE SO THERES NO NEED FOR THE RUBBERDUCKY TO GET THE LANGUAGES FILES FROM THE FOLDER INTO FIRMWARE. ITS JUST THERE FOR UNDERSTANDMEND.



The language/keyboard layout files (JSON) are **purely for the compiler's understanding** - they do NOT get embedded into the firmware or `inject.bin`.

### What Actually Happens

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│  Language JSON  │────▶│   Compiler      │────▶│   inject.bin    │
│  (on your PC)   │     │   (translates)  │     │  (raw keycodes  │
│  "a": "00,00,04"│     │   "a" → 0x04    │     │   only)         │
└─────────────────┘     └─────────────────┘     └─────────────────┘
                                                          │
                                                          ▼
                                                  ┌─────────────────┐
                                                  │  Rubber Ducky   │
                                                  │  (just receives│
                                                  │   0x04, 0x00)  │
                                                  └─────────────────┘
```

### The Language File is a Compile-Time Tool

When you compile a payload:

1. **Your PC** reads the JSON language file
2. **The compiler** replaces `STRING Hallo` with raw bytes like `0b 02 04 00 0f 00 0f 00 12 00`
3. **Only those raw bytes** go into `inject.bin`
4. **The Rubber Ducky** never sees the word "Hallo" or the JSON - it just gets byte commands

### Evidence from the Code

Looking at your `handleString()` function:

```javascript
function handleString(line) {
    let args = getArgsFromLine(line);  // Gets "Hallo"
    let tmp = [];
    for (let i = 0; i < args.length; i++) {
        let ch = args.charAt(i);        // 'H', 'a', 'l', 'l', 'o'
        let ba = getBytesForKey(ch);    // Looks up in JSON ON YOUR PC
        tmp.push(ba[0]);                // Pushes ONLY the keycode
        tmp.push(ba[1]);                // Pushes ONLY the modifier
    }
    return tmp;  // Returns raw bytes like [0x0b, 0x02, 0x04, 0x00, ...]
}
```

The `appendHexStringArray()` function then writes these raw bytes to `oBB` (the output buffer), which becomes `inject.bin`.

### The Rubber Ducky's Firmware

The device firmware only understands:
- **Keycodes** (like `0x04` for "a/A")
- **Modifier bits** (like `0x02` for Shift)
- **Delays** (like `00 FF` for 255ms)

It has **NO concept** of:
- JSON files
- Keyboard layout names
- Character strings like "Hallo"
- The word "EXTENSION" or "STRING"

### Why Language Files Exist at All

They're **developer tools** that let you:

1. **Write portable payloads** - Same DuckyScript works for different target keyboards
2. **Compile once, run anywhere** - The compiler handles the translation
3. **Support special characters** - Like German `ä`, `ö`, `ü` by mapping them to the correct keycodes for that layout

### Example: Same Payload, Different Layouts

**DuckyScript:** `STRING Hallo Welt`

| Target Layout | Language File Used | inject.bin Contains |
|---------------|-------------------|---------------------|
| German | `"ä": "00,00,34"` | Bytes for German keyboard positions |
| US | `"a": "00,00,04"` | Bytes for US keyboard positions |

**The compiled `inject.bin` is DIFFERENT** for each target layout, even though the source code is identical.

### Your Understanding is Correct

> "LANGUAGE KEYCODES GET COMPILED INTO THE FIRMWARE"

More precisely: The **keycodes** (not the language definitions) get compiled into the `inject.bin` file that gets **uploaded** to the device's firmware storage. The device just executes these raw keycode instructions.

The JSON files are **never** sent to the device - they exist only on your computer to help the compiler know what bytes to generate.
